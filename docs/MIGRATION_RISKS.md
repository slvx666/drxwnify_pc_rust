## 2. Глубокий анализ ключевых рисков и превентивные меры

### 2.1. Риск 1: Декодирование HLS AES-128 в VK Music
- **Техническая природа проблемы:** В отличие от стандартных MP3 файлов, аудиозаписи ВКонтакте часто отдаются в формате HLS-плейлиста (`index.m3u8`), разбитого на чанки TS или AAC по 2–5 секунд, зашифрованные симметричным ключом AES-128. Ключ отдается по отдельному HTTPS-адресу из тега `#EXT-X-KEY`. Большинство чистых Rust-аудиобиблиотек (например, Symphonia или Rodio) не умеют парсить m3u8 плейлисты и запрашивать ключи шифрования по сети.
- **Архитектурное решение:** В Rust Core аудиодвижка (`drxwnify-audio`) используется библиотека `ffmpeg-next` (или прямой FFI биндинг к libavformat). В сборку FFmpeg включаются протоколы `hls`, `crypto`, `http`, `https` и демуксер `hls`. FFmpeg берет на себя прозрачную загрузку сегментов, дешифрование и выдачу единого непрерывного потока PCM сэмплов.
- **Стратегия отката (Fallback):** В `VkSource.kt:35` адреса `/[0-9a-f]+(/audios)?/([0-9a-f]+)/index\.m3u8` предварительно проверяются на наличие прямого MP3 файла на том же сервере. Если прямого файла нет, а HLS дает сбой более 12 секунд (срабатывает Watchdog), трек автоматически переключается на YouTube резерв без прерывания пользовательского сценария.

### 2.2. Риск 2: Стабильность YouTube InnerTube API
- **Техническая природа проблемы:** Google периодически меняет формат ответов InnerTube API, вводит проверки n-параметра (signature cipher) и блокирует сторонние User-Agent кодами 403 Forbidden.
- **Архитектурное решение:**
  1. В `drxwnify-sources` реализована ротация трех независимых мобильных клиентов:
     - `YouTubeClient.VISIONOS` (клиент Apple Vision Pro) — исторически самый стабильный клиент, отдающий прямые, незашифрованные ссылки на цельные WebM файлы с presigned параметрами.
     - `YouTubeClient.ANDROID_VR_1_65_10` — второй резервный клиент.
     - `YouTubeClient.ANDROID_VR_1_43_32` — третий резервный клиент.
  2. В качестве аварийного шлюза (last resort) сохраняется алгоритм NewPipe (извлечение muxed itag 18 AAC 96 kbps).

### 2.3. Риск 3: Пиксельная точность размытия Haze Blur в UI
- **Техническая природа проблемы:** В Compose Desktop библиотека `haze` работает через Skia Direct3D GPU шейдер. В Rust-фреймворках (Slint, Iced, egui) нет встроенного нативного композитинга произвольного размытия с наложением полупрозрачных слоев.
- **Архитектурное решение:** Выбор **Tauri 2.0** полностью снимает этот риск. В WebView2 размытие `backdrop-filter: blur(28px) saturate(180%)` выполняется встроенным DirectComposition движком Windows на уровне видеочипа с минимальным расходом ресурсов и 100% пиксельным соответствием оригинальному матовому стеклу.

### 2.4. Риск 4: Конфликт пользовательских данных
- **Техническая природа проблемы:** Если обе версии приложения (Kotlin и Rust) будут одновременно запущены пользователем и начнут писать в одну директорию `%APPDATA%\Drxwnify`, неизбежна перезапись файлов `queue.json` и `library.json` с повреждением данных.
- **Архитектурное решение:**
  1. Рабочая директория Rust-версии строго изолирована: `%APPDATA%\DrxwnifyRust\`.
  2. Порт SingleInstance изменен на `47834` (оригинал слушает `47833`).
  3. Имя исполняемого файла: `Drxwnify.exe` (в установщике `Drxwnify-Rust-Setup.msi`).
  4. При первом старте Rust-версия предлагает пользователю: «Импортировать медиатеку и настройки из предыдущей версии Drxwnify?». При согласии файлы безопасно копируются в новую директорию, а оригинальные файлы остаются нетронутыми.
